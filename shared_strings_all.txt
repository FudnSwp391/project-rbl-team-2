50: IMPLEMENTATION
51: CV Text Extraction & Validation / cvAnalysisService
52: Tải và trích xuất text từ file PDF/DOCX trên Frontend thường bị lỗi định dạng (mất dòng, chữ dính nhau) và ứng dụng dễ bị crash khi người dùng tải lên file CV trống, ảnh quét scan hoặc CV đùa giỡn (joke CV).
53: Tôi muốn viết hàm trích xuất text từ file PDF (dùng pdfjs-dist) và DOCX (dùng mammoth) trong React. Hãy viết code tối ưu sắp xếp văn bản theo dòng dựa trên tọa độ Y và X của các khối chữ trong PDF. Đồng thời viết thêm logic tiền kiểm tra (validation) để phát hiện và từ chối các file CV trống, file scan chỉ có ảnh, hoặc các CV có nội dung đùa giỡn không nghiêm túc trước khi gọi API.
54: Đề xuất thuật toán sắp xếp tọa độ Y (top-to-bottom) và X (left-to-right) của các item từ getTextContent() để ghép dòng chính xác. Cung cấp hàm validateCVContent sử dụng Regex đếm số lượng từ thực tế và nhận diện các mẫu từ khóa đùa giỡn (troll, meme, ctrl+c, ctrl+v, v.v.).
55: Phản biện AI: Nhận thấy nếu PDF không có text (chỉ có ảnh quét scan), việc gọi API vẫn tốn token vô ích. Do đó việc đếm số lượng từ có nghĩa (ít hơn 5 từ chuyên môn) là rào cản cực tốt để chặn trước khi gửi request.
56: Áp dụng cấu hình pdfjsLib.GlobalWorkerOptions.workerSrc trỏ trực tiếp đến local node_modules trong dự án React Vite thay vì dùng CDN bên ngoài để tránh lỗi không đồng bộ phiên bản khi dev offline.
57: Ráp nối bộ lọc tiền kiểm tra (Pre-validation) với service phân tích chính. Nếu không vượt qua kiểm tra, trả về ngay cấu trúc báo cáo lỗi chuẩn chỉnh với điểm ATS = 0 mà không cần gọi API Gemini.
58: Quyết định cài đặt bộ quy tắc nghiêm ngặt trên Frontend để loại bỏ các CV troll, bảo vệ hạn mức sử dụng (quota) của Gemini API và nâng cao độ tin cậy của dịch vụ.
59: DEBUGGING
60: API Rate Limit Handling / interviewAiService
61: Khi nhiều người dùng cùng lúc trải nghiệm Mock Interview, hệ thống liên tục trả về lỗi HTTP 429 (Too Many Requests) từ Groq/Gemini API miễn phí, gây gián đoạn luồng phỏng vấn của ứng viên.
62: Tôi đang gặp lỗi Rate Limit (429) khi gọi API của Groq và Gemini trong ứng dụng phỏng vấn. Hãy hướng dẫn cách xây dựng cơ chế tự động thử lại (auto-retry) dựa trên thời gian chờ yêu cầu của API và thiết lập cơ chế dự phòng (fallback) tự động chuyển sang mô hình Gemini nếu Groq bị lỗi hoàn toàn.
63: Đề xuất viết hàm bao bọc callGroq có tham số retryCount. Nếu nhận mã 429, dùng Regex trích xuất thời gian chờ từ phản hồi lỗi (try again in Xs), trì hoãn bằng setTimeout và thử lại tối đa 1 lần. Nếu tất cả các model Groq thất bại, tự động nhảy sang hàm callGemini làm dự phòng.
64: Phân tích AI: Cơ chế retry của AI gợi ý là đúng đắn, nhưng cần đặt thời gian chờ tối đa (max wait 35s) để tránh việc ứng viên phải chờ đợi quá lâu trên màn hình loading gây ức chế.
65: Đồng bộ hóa luồng lỗi với giao diện phòng phỏng vấn (InterviewRoom.jsx). Nếu API hoàn toàn thất bại sau các lượt thử, hiển thị màn hình báo lỗi trực quan (room-error-screen) có nút 'Thử lại' và 'Quay lại thiết lập' thay vì crash ứng dụng.
66: Tích hợp cả cơ chế xoay vòng model của Groq (llama-3.3-70b sang llama-3.1-8b) và fallback sang Gemini trong một service duy nhất, tạo ra hệ thống chịu lỗi (fault-tolerant) 3 lớp.

67: Quyết định tự chủ triển khai luồng xử lý lỗi thông minh thay vì chỉ hiển thị thông báo lỗi đơn thuần, ưu tiên trải nghiệm mượt mà của ứng viên làm tiêu chí hàng đầu.
